PHASE 2: ARCHITECTURE AND IMPLEMENTATION
Use Manifest V3, vanilla JavaScript or TypeScript, namespaced CSS and only small
local tooling. React and a web server are unnecessary for the delivered package.
Choose the structure, e.g. manifest.json, content script, service worker,
badge.css, local LV/EN messages/settings, icons, tests, README and build script.

Content script:
- Run only on exactly approved Barbora origin/path layouts. Exclude basket,
  account, personal-history and checkout areas even if their markup contains IDs.
- Prefer verified product roots and exclude repeated/nested representations.
  If root and child IDs disagree or scope is ambiguous, do not display a badge.
- Extract exact SKU strings, deduplicate and batch. Debounce a scoped observer;
  bound work, prioritize visible products and do not rescan all DOM per mutation.
- Ignore extension-owned mutations to avoid observer loops.
- Detect full document loads, supported SPA changes and lazy-loaded products.
  Use a robust lifecycle without assuming mutations always signal a URL change.
- When cards are reused or an ID changes, remove the old badge immediately.
- Before applying async results recheck node connectivity, current SKU and
  eligible location; stale requests must not attach a grade to another product.
- Render exactly one badge per intended visible card/main detail presentation,
  not once per child link, analytics wrapper or sticky detail duplicate.
- Use dedicated non-interactive placement. Never nest anchors in anchors/buttons,
  cover retailer labels, change prices, intercept add-to-cart or alter navigation.

Service worker:
- Make API requests from the worker, not from the page-origin content script.
- Accept only a fixed lookup message with validated SKU array.
- Verify sender is this extension and its tab URL has the exact approved Barbora
  origin. No externally_connectable bridge or arbitrary page postMessage API.
- Never accept an arbitrary fetch URL, HTTP headers or code from content messages.
- Use one fixed ABCDE HTTPS endpoint, POST JSON, credentials:"omit", redirect:"error",
  bounded timeout (e.g. 5 seconds), at most 2 concurrent requests and finite queue.
- Validate JSON/schema, requested-key subset, A–E grades and canonical links.
  Allow optional links only to the approved ABCDE HTTPS product path; no HTML
  rendering. A missing link is legitimate: display a non-clickable badge.
- Respect Retry-After and cap retries. Service failures must not enter miss cache.
- Bounded memory caches, e.g. max 2,000 entries, positive TTL 10 minutes,
  actual missing-grade TTL 60 seconds. Deduplicate in-flight lookups.
  Worker suspension may clear caches; do not store browsing history to avoid it.

Permissions:
- Only precise Barbora content-script matches and ABCDE API host access.
  No <all_urls>, cookies, history, webRequest or broad tabs permission.
- If storage is used, store only chosen language/settings, not SKUs or activity.
- Bundle every executable script locally. No remote JavaScript, eval, tracking,
  externally supplied code, production credentials or supposedly secret API key.
- Use safe message passing and treat DOM/API values as untrusted data.

Badge/messages:
- Compact letter badge with ABCDE attribution, not a claim of native Barbora
  endorsement or official Nutri-Score artwork. Check artwork rules before using
  official assets. Avoid overstating freshness or scientific status.
- Proposed backgrounds: A #038141, B #85BB2F, C #FECB02, D #EE8100, E #E63E11.
  Select accessible text colors; include the letter so color is not sole meaning.
- LV: "Nutri-Score: D — ABCDE.lv"; EN: "Nutri-Score: D — ABCDE.lv".
  Localize settings, errors, aria labels and independent-source explanation.
- Clicking a badge with a validated link opens ABCDE in a new tab using
  rel="noopener noreferrer". No link available: keep the badge non-clickable.
- The currently verified product canonical is Latvian; English product addresses
  can redirect to Latvian. Do not promise English destination pages.
- Missing/invalid/ambiguous grade means no badge, never a guessed grade.
- API outage means no new badge and an optional unobtrusive extension status,
  not repeated alerts or a fake "no Nutri-Score" statement.
- Debug off by default; counts/status/timings only, no names, SKU lists, page
  queries, cart data or personal browsing details in persistent logs.
